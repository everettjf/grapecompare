# GrapeCompare 1.3 — Safe File Operations

## Outcome

Version 1.3 turns a folder comparison into an explicit, reviewable operation plan. Users can choose individual or multiple differences, queue left-to-right or right-to-left actions, preview the real filesystem impact, execute with progress and cancellation, and undo a completed transaction when its outputs have not changed.

## Product rules

1. Comparison never mutates the filesystem. Every mutation starts as a queued draft and requires a separate review and confirmation step.
2. Copy creates a missing destination. Replace is a distinct, clearly labelled action and always retains the displaced destination as an undo backup.
3. Move is offered only when the destination does not exist. A same-volume move is atomic where the filesystem supports it. A cross-volume move is copy, byte-for-byte verification, destination commit, then source-to-Trash.
4. Delete always means “Move to Trash”. Version 1.3 has no permanent-delete command.
5. Folder counts and byte estimates come from a fresh preflight scan, including hidden and normally ignored comparison entries. Symbolic links are operated on as links and are never followed.
6. Immediately before each commit, the engine rechecks the source and destination snapshots captured by preflight. Stale plans stop safely instead of overwriting newer work.
7. Cancellation is cooperative. It stops before the next item or during staged folder copying, removes incomplete staging data, and never interrupts an atomic commit.
8. Undo runs in reverse order and refuses to replace an output that has changed since execution. In-session undo is guaranteed for successful operations; items moved to the system Trash remain manually recoverable after the app exits.
9. A process-wide execution lock serializes transactions from multiple windows. Each transaction still performs its own precondition checks after acquiring the lock.
10. The comparison is refreshed after execution and after undo so the UI never presents a knowingly stale tree.

## User flow

1. Select one or more rows in the comparison tree.
2. Queue Copy, Move, or Move to Trash for the left or right side. Individual row arrows provide the fast copy/replace path.
3. Open **Review Plan**. Preflight resolves each draft to its concrete source and destination, counts items and bytes, and shows warnings for replacement, folders, moves, and Trash actions.
4. Confirm **Execute Plan**. The sheet displays completed items, bytes, the current relative path, and a Cancel button while work is cancellable.
5. Review the result. Successful transactions expose **Undo Last Operation** in the sheet and Edit menu. Partial failures remain visible and do not conceal already completed work.

## Implementation phases

### Phase A — transaction core

- Stable operation, snapshot, plan, progress, result, transaction, and undo models.
- Preflight with overlap de-duplication, real folder impact, stale-plan validation, and symlink-safe traversal.
- Staged copy/replace, same- and cross-volume move, Trash deletion, rollback metadata, global serialization, and cooperative cancellation.
- Unit tests use an injected Trash directory; tests never alter the user’s real Trash.

### Phase B — planning and review UI

- Stable multi-row selection using `Set<FolderNode.ID>`.
- Per-row left/right copy controls plus bulk Copy, Move, and Move to Trash menus.
- A plan bar and item-driven review sheet with impact summary, warnings, explicit destructive confirmation, progress, cancellation, per-item failures, and undo.
- Native keyboard/menu undo for the most recently completed in-session transaction.

### Phase C — release integration

- Enable the App Sandbox user-selected read/write entitlement.
- Localize all new visible strings in English and Simplified Chinese.
- Refresh the comparison after mutation, document the feature and safety contract, update the changelog, and set version 1.3.0 (build 7).

## Acceptance gates

- Copy-missing, replace-with-backup, same-volume move, Trash, and undo each have passing integration tests.
- A changed source/destination invalidates execution; a changed output invalidates undo.
- Folder preflight counts hidden entries; symlink tests prove the target is untouched.
- Cancellation leaves no committed partial destination and no leaked staging data.
- Debug and unsigned Release builds succeed with the App Sandbox read/write entitlement.
- Existing comparison and diff tests remain green.

## Deferred beyond 1.3

- Persistent undo journals across app relaunches.
- Permanent deletion and secure erase.
- Conflict merging or automatic two-way synchronization.
- Scheduled/background synchronization and network-volume resume.
