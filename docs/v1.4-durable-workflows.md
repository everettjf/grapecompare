# GrapeCompare 1.4 — Durable Operation Workflows

## Outcome

Version 1.4 makes safe file-operation plans reusable and recoverable beyond one sheet or one app session. Completed transactions are journaled atomically, operation history remains visible after relaunch, progress reports throughput and an estimated remaining time, users choose whether a batch stops or continues after an item failure, and relative-path plan recipes can be exported and imported against the currently compared folder pair.

## Product rules

1. Every successful commit is written to an atomic, versioned undo journal before it is presented as durable history.
2. Journal entries retain the exact snapshots and backup locations required by the 1.3 safety checks. Relaunch does not weaken stale-output or collision protection.
3. Security-scoped bookmarks are retained for the nearest available operation directories. Failure to create a bookmark never makes the journal unreadable; inaccessible entries fail safely at undo time.
4. Undo remains stack ordered. Only the newest transaction may be undone, so a later transaction can never be silently bypassed.
5. History is bounded. Removing an old entry cleans up private replacement backups, but never empties or permanently deletes items in the system Trash.
6. Batch failure behavior is explicit: **Stop on First Failure** or **Continue After Failures**. Cancellation always takes precedence and stops before the next safe commit.
7. Progress uses committed bytes when available and operation count otherwise. Throughput and estimated remaining time are advisory and never affect commit safety.
8. Exported recipes contain only operation kind, source side, and validated relative paths. They do not contain file contents, credentials, absolute paths, undo metadata, or security bookmarks.
9. Imported recipes are resolved strictly below the currently selected left and right roots. Absolute paths, `..`, empty paths, duplicate IDs, and unsupported schema versions are rejected before anything is queued.
10. Journal and recipe decoding is schema-versioned. Corrupt journals are quarantined instead of overwritten; invalid recipe imports do not alter the current queue.

## User flow

1. Queue operations as in 1.3, then optionally export them as a `.grapeplan` recipe.
2. In the review sheet, choose the batch failure behavior and inspect the resolved filesystem impact.
3. Execute. The progress view reports items, bytes, transfer speed, and estimated time remaining when enough data exists.
4. Open **History** to inspect durable transactions. The latest entry can be undone now or after relaunch while its outputs remain unchanged.
5. On another matching folder pair, import a `.grapeplan`; GrapeCompare validates and maps the relative operations to the selected roots, then adds them to the normal review queue.

## Acceptance gates

- Journal save/load, atomic replacement, corrupt-file quarantine, retention, and removal have automated coverage.
- A transaction executed by one controller instance can be loaded and safely undone by a new controller/engine instance.
- Persisted undo still refuses changed outputs and collisions without deleting user data.
- Both failure policies are tested with a multi-item plan whose middle item becomes stale.
- Progress estimation is deterministic under an injected clock and never emits negative or non-finite values.
- Recipe round-trip, root remapping, path traversal rejection, schema rejection, and non-mutating failed import are tested.
- Existing 1.0–1.3 comparison and safe-operation tests remain green.
- Debug and unsigned Release builds succeed; the built app reports version 1.4.0.

## Deferred beyond 1.4

- Undoing transactions out of stack order.
- Automatic conflict merging or continuous two-way synchronization.
- Scheduled/background execution and interrupted network-volume resume.
- Permanent deletion and secure erase.
